# Open File Lines

[English](README.md) · **Русский**

Поставьте курсор на ссылку с путём в любом тексте, нажмите **Alt+P** — файл откроется, а указанные строки окажутся выделены.

```text
episodes/e03.md            -> открывает файл, ничего не выделяет
episodes/e03.md:300        -> открывает файл, переходит на строку 300 и выделяет её
episodes/e03.md:494-586    -> открывает файл, переходит на строку 494 и выделяет строки 494..586
```

Обрамление ссылки бэктиками или кавычками ничего не меняет — `` `episodes/e03.md:494-586` `` работает точно так же, как голая форма. То же касается markdown-ссылок, `<угловых скобок>` и ссылок, за которыми идёт запятая или точка.

## Установка

[![Marketplace](https://vsmarketplacebadges.dev/version/bytecoded.open-file-lines.svg?style=flat&label=VS%20Code%20Marketplace&logo=visualstudiocode)](https://marketplace.visualstudio.com/items?itemName=bytecoded.open-file-lines)

Найдите *Open File Lines* в панели Extensions или выполните:

```bash
code --install-extension bytecoded.open-file-lines
```

## Команды и клавиши

| Клавиши | Команда | Что делает |
| --- | --- | --- |
| `Alt+P` | `Open File Lines: Open File at Cursor` | открывает в активной группе редактора |
| `Alt+Shift+P` | `Open File Lines: Open File at Cursor to the Side` | открывает в группе сбоку |

Обе команды есть и в контекстном меню редактора. Если в редакторе что-то выделено, ссылкой считается выделение, а не токен под курсором.

## Синтаксис ссылок

| Форма | Результат |
| --- | --- |
| `path` | только открыть |
| `path:300` | выделена строка 300 |
| `path:494-586` | выделены строки 494..586 |
| `path#L494-L586`, `path#300` | то же самое, в стиле якорей GitHub |
| `path:300:12` | курсор на строке 300, колонка 12, ничего не выделено |
| `https://…` | передаётся системному браузеру |

Диапазон, записанный задом наперёд (`path:586-494`), читается как тот же самый. Номера строк за пределами файла подтягиваются к последней строке. Форма `path(300,12)` *не* поддерживается: скобка обязана завершать ссылку, чтобы продолжало работать `[text](path:1-2)`.

## Как ищется путь

Побеждает первый существующий вариант:

1. абсолютные пути (включая `C:\…`, `file://…`, `~/…`, `${workspaceFolder}/…`, `${userHome}/…`, `%VAR%`) — как есть;
2. относительно папки файла, в котором находится ссылка;
3. относительно каждого корня рабочей области, начиная с того, которому принадлежит текущий файл;
4. относительно каждой папки из `openFileLines.searchPaths`.

Если у ссылки нет расширения, по очереди пробуются расширения из `openFileLines.extensions`. Когда не подошло ничего, появляется предупреждение с кнопкой **Show searched paths** — она выводит все проверенные места в канал вывода *Open File Lines*. Ссылка на папку раскрывает её в проводнике.

## Настройки

| Настройка | По умолчанию | Смысл |
| --- | --- | --- |
| `openFileLines.searchPaths` | `[]` | дополнительные папки для поиска; относительные записи разрешаются относительно папки текущего файла и каждого корня рабочей области |
| `openFileLines.extensions` | `[".md", ".txt", ".ts", ".js", ".json"]` | расширения, которые пробуются, если у ссылки его нет; `[]` отключает угадывание |
| `openFileLines.delimiters` | `` `'"<>|*?,;!=&^()[]`` плюс пробел и табуляция | символы, завершающие ссылку, когда она берётся из текста вокруг курсора |
| `openFileLines.selectLines` | `true` | выделять диапазон; если выключено, только перемещается курсор |
| `openFileLines.preview` | `false` | открывать в режиме предпросмотра (переиспользуемая вкладка курсивом) |

## Разработка

```bash
npm install
```

```bash
npm test
```

`npm test` прогоняет наборы тестов на парсинг и разрешение путей на чистом node — экземпляр VSCode не нужен. По `F5` запускается Extension Development Host; в `samples/links.md` лежат ссылки, которые можно попробовать на `samples/episodes/e03.md` — это файл из 600 пронумерованных строк.

## Локальная установка без упаковки

Сначала удалите версию из маркетплейса. Две копии дают одни и те же команды и обе вешаются на `Alt+P`, а VSCode выбирает между ними по порядку сканирования:

```bash
code --uninstall-extension bytecoded.open-file-lines
```

Затем скопируйте или слинкуйте эту папку в каталог расширений и перезапустите VSCode:

```bash
cmd //c mklink //d "%USERPROFILE%\.vscode\extensions\bytecoded.open-file-lines" "D:\Me\Projects\vscode-open-file-lines"
```

Имя папки — соглашение, а не требование: идентификатор VSCode читает из `package.json`. Но `publisher.name` держит её в одном ряду со всеми остальными записями в этом каталоге.

Либо соберите `.vsix`:

```bash
npx @vscode/vsce package
```

## Предыстория и зачем это нужно

Работа с токеном под курсором, запасные пути поиска и подстановка расширений повторяют поведение [Fr43nk.seito-openfile](https://marketplace.visualstudio.com/items?itemName=Fr43nk.seito-openfile) — зрелого и активно поддерживаемого расширения в этой нише. Его механизм разрешения путей заметно богаче, чем я сделал тут: маппинг ведущих участков пути, поиск по подпапкам с глобами, подстановка расширений в зависимости от языка, откат к quick-open. Если вы указываете на обычные пути в коде и в выводе терминала — берите его.

А это расширение существует потому, что оптимизировано под ссылки внутри прозы. Заметки, комментарии ревью, расшифровки — текст, где ссылка стоит посреди предложения, обёрнута пунктуацией и указывает на диапазон строк, а не на конкретную строку. Например, вот строка из тех заметок, ради которых всё и писалось:

```text
- Она говорит коротко и прямо. (/episodes/e01.md:448-487; /episodes/e01.md:972-1012)
```

Здесь одновременно должны выполняться три требования:

1. **Диапазон обязан пережить токенизацию.** `:` и `-` должны остаться *внутри* токена, иначе `448-487` перестаёт быть диапазоном, — но всю остальную пунктуацию вокруг надо срезать. Для этого нужны два раздельных механизма: набор разделителей, завершающих токен, и отдельный проход обрезки обрамляющей пунктуации (`DEFAULT_DELIMITERS` и `TRIM_LEADING` / `TRIM_TRAILING` в `src/parse.js`). Один класс символов «границы слова» не в состоянии выразить «`(` завершает токен, а `-` нет, и точка в конце — это пунктуация, а не часть имени».

2. **Круглые скобки обязаны быть разделителями**, а значит, приходится отказаться от формы `path(300,12)`, принятой в диагностике компиляторов. Размен сделан осознанно: markdown-ссылки и замечания в скобках в прозе повсюду, а диагностика MSVC — нет. Расширение, нацеленное на вывод сборки, должно решать наоборот — seito-openfile так и делает, поэтому ссылка вида `(path:448-487` там не разрешается.

3. **Битый диапазон не должен молча срабатывать.** При нестрогом разборе `path:972-1012` даёт строку 972: файл открывается, диапазон тихо отбрасывается, и внешне всё выглядит правильно. Здесь позиционный суффикс разбирается регулярками с якорями, поэтому ссылка либо распознаётся как диапазон, либо целиком остаётся частью пути.
